# 老板与产品经理：从业务问题走到试点

[首页](../README.md) · [English](business-playbook.en.md) · [工作表](../WORKSHEET.md) · [本地业务测算器](https://codyqin.github.io/ai-task-compass/business-calculator.html)

本项目交付分析协议、选型参考、设计蓝图和试点工具，不是已经接好你业务系统的全自动平台。先确定值得解决的问题，再选技术。

## 1. 老板先决定：改善什么、为什么现在做

| 必须说清 | 问法 | 需要证据 |
|---|---|---|
| 工作对象与责任人 | 谁在什么时点收到什么、要交付什么？ | 一次近期完整样本、现有负责人 |
| 基线 | 每月几次、每次执行和返工多久？ | 实际记录，估计需标注 |
| 业务结果 | 减少什么错误，改善哪个交付，而非“提高智能化”？ | 质量口径、谁验收、观察窗口 |
| 约束 | 数据授权、地域、预算、工具、维护能力？ | 能使用的实际条件 |
| 收益归属 | 省时能怎样重新利用？是否真的减少支出或增加毛利？ | 不能把员工工资×省时自动算现金收益 |

不要把“大家都忙”直接转换成采购需求。可能先改责任、规则或资料版本，也可能普通软件足够。

## 2. 产品经理再决定：拆什么、交付到哪里

画出现有流程的输入→动作→检查→交付，标等待点、异常和数据所有者。按环节判断信息处理需求和控制路径，而不是给整个公司打一个象限标签。

每个候选环节写一张卡：**用户、触发条件、输入与权限、输出格式、禁止补造的信息、异常、人工接管、验收、日志、维护人**。暂时不知道的字段保留未知；只补会改变下一步的缺口。

## 3. 排候选，不做伪精确总分

先看：是否有明确交付和验收？资料能合法取得？错误可检测并有负责人接管？有足够频率值得比较全成本？有维护人？缺条件时给“先澄清/先准备资料/小试点”，不直接判定不可做或一定高 ROI。

接着比较两条路线：已有工具的小版本，和仅在必要时采用的平台/工程版。分别说明收益假设、工作量、权限与维护条件、停止条件。示意评分可以讨论，不能冒充科学测量或替代老板的取舍。

## 4. 最小 PRD：可以直接交给实施者

```text
问题与目标用户：
当前流程及可观察的基线：
试点只覆盖的环节与明确不覆盖的动作：
输入来源、版本、数据使用授权：
输出字段与来源证据要求：
验收样本（典型、异常、缺失、冲突）与检查人：
质量/耗时阈值（提议后由业务方确认）：
人工确认、失败接管、重试与最大调用预算：
日志留存、访问控制、维护人与回滚方式：
首次试点、复盘时间、继续/调整/停止条件：
```

## 5. 同时量质量、时间和钱

- 质量例：重要问题漏报率、无依据事实数、人工改动量。定义分母和错误严重度；不能仅看语言流畅度。
- 时间：相同工作量和质量口径下，比较准备+执行+检查+返工，维护另列。
- 钱：初始投入、每月平台/模型费、维护现金支出，与有证据的现金节省、增量毛利、减少损失分开。
- 量化前先测：每次模型调用次数、输入输出 token、重试、检索、人工接管；不能只用一次对话成本代表整套业务成本。
- ROI 和回本期是条件测算，非承诺。质量不达标时不能凭省时就宣告成功。

打开 [测算器](https://codyqin.github.io/ai-task-compass/business-calculator.html) 输入自己的假设；页面不调用模型、不上传数据。货币单位由你统一，不能混合不同币种。高风险项目还需相应专业评估，本工具不代替审批。

## 6. 从试点到上线

先人工观察一批获授权样本，再小范围使用；确认负责人、日志和接管后逐步扩大。持续记录错误类型、模型/提示词版本、资料更新和总成本。模型、检索或流程变化后重跑保留样本。不要把一个成功演示当稳定生产系统。
