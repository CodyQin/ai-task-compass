# 为什么这样设计：创业验证与 AI 工程

[首页](../README.md) · [English](design-rationale.en.md)

这些资料为具体设计选择提供依据，不是对本项目效果的认证。研究观点、我们的应用归纳和仍需实际试用的假设分开；不把一份规划框架称为“已科学证明能让业务成功”。

| 设计选择 | 一手参考与核心意思（意译） | 项目如何应用 | 不能推出什么 |
|---|---|---|---|
| 先澄清真实问题，再选方案 | [Steve Blank 的客户开发方法](https://steveblank.com/category/customer-development-manifesto/)：把早期设想当假设，以外部观察和实验学习 | 分开事实、假设、用户/付费者，留下支持/反驳条件 | AI 生成的人设或对话不算真实需求、支付验证 |
| 试点先约定能承受的投入 | [Effectuation 的 affordable loss](https://effectuation.org/the-five-principles-of-effectuation)：不确定下先考虑可承担的损失 | 记录时间/现金上限、学习目标、停止与复盘 | 不证明试点有利可图，也不替代财务或风险判断 |
| 固定流程与自适应控制分开 | [Anthropic 的 workflow/agent 区分](https://www.anthropic.com/research/building-effective-agents) | 四象限只帮助方案阶段选控制方式，优先简单路线 | 四象限不是其论文原图；自适应不必用模型 Agent |
| 先约定验收，再比较模型和系统 | [Anthropic 的 Agent 评测工程实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) | 用具体交付、典型/异常样本和错误口径定义成功 | 少量样本不能证明普遍可靠，榜单不能代替自己的验收 |

## 从资料中实际改了什么

1. **从象限分类入口改为问题入口。**先判断用户在探索需求、设计方案、评测还是试点；只在需要时分类任务。
2. **从散落模板改为同一份简报。**每一步保留证据、未知和用户纠正，交给下一步继续；不重复编一个业务背景。
3. **新增需求假设与学习实验。**创业/自媒体的想法不直接转换成工具采购，先写什么现象会支持或推翻设想。
4. **试点补上投入上限与停止条件。**计算收益只是条件估计，先保护试点可控、可学习。
5. **允许跳过。**已确定的需求无需无限访谈；一次性简单任务不用完整跑一遍业务规划。

## 怎样知道这套设计有没有帮助

在获授权、脱敏任务上观察：是否少重复提问，事实是否被保留，交付是否可验收，下一步能否执行，真实检查/返工成本怎样。比较同等任务条件下的实际过程，允许结果证明某个模块无用或过重。不因为资料丰富、Star 或收藏多就宣布用户价值成立。

不适用场景：紧急的一步操作、已经明确到可以直接执行的小问题，通常不需要完整合集。反例：如果四个模块不断重复问题、交接更慢，应该减少流程而不是增加提示词。
